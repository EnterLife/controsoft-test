# Тестовое задание QA: монитор сигналов

## Допущения

В исходных данных не указаны имена исполняемых файлов, заголовок окна и формат
TCP-сообщений. Поэтому тест ниже:

- использует выданный сервис-симулятор как источник данных и не дублирует
  неизвестный протокол;
- принимает команды запуска приложения и симулятора через параметры pytest;
- работает с внешним Linux/Qt-приложением через AT-SPI accessibility tree;
- опирается только на заявленный пользовательский контракт: кнопка
  «Подключиться», таблица из пяти колонок и 10 сигналов;
- предполагает, что приложение уже настроено на локальный сервис и порт 2001.

Перед включением теста в CI я бы уточнил протокол и заменил внешний симулятор
на детерминированный TCP stub. Тогда можно было бы проверять не только структуру
и типы отображённых данных, но и точное соответствие каждого значения
отправленному пакету.

Dogtail выбран как бесплатный Python-инструмент для black-box автоматизации
Linux desktop через AT-SPI. Его поддержка Qt ограничена, поэтому до начала
автоматизации нужно проверить accessibility tree конкретной сборки. Если
`QTableView` не публикует строки и ячейки, потребуется исправление accessibility
в приложении либо согласованный GUI-инструмент с полноценной поддержкой Qt
(например, Squish); подмена UI-теста координатными кликами не рассматривается
как надёжное решение.

## Чек-лист (15 проверок)

1. Приложение запускается без ошибок; главное окно содержит таблицу с колонками
   `ID`, `Имя`, `Значение`, `Качество`, `Время` и кнопки «Подключиться» и
   «Обновить».
2. При работающем сервисе на порту 2001 приложение подключается и отображает
   ровно 10 сигналов; все обязательные поля заполнены и имеют корректный тип.
3. Значения и время сигналов обновляются при поступлении новых данных, строки не
   дублируются и соответствуют своим ID.
4. Кнопка «Обновить» запрашивает актуальные значения; интерфейс остаётся
   отзывчивым, время данных не уменьшается.
5. При недоступном сервисе/закрытом порте показано понятное сообщение, окно не
   зависает и пользователь может повторить подключение.
6. Разрыв TCP-соединения корректно отражается в UI; устаревшие данные нельзя
   принять за актуальные, повторное подключение восстанавливает работу.
7. Частичный, склеенный или повреждённый TCP-пакет не приводит к падению;
   ошибка фиксируется в логе, следующий корректный пакет обрабатывается.
8. Дубликаты, пропуски и неизвестные ID обрабатываются по требованиям без
   повреждения или неверной адресации строк.
9. Граничные значения (`0`, отрицательные, min/max, `NaN`, `Inf`) и длинные/
   Unicode-имена отображаются предсказуемо и не ломают разметку.
10. Изменение качества сигнала отображается в нужной строке и визуально
    отличимо от нормального состояния.
11. Время отображается в согласованном формате и часовом поясе; старый пакет не
    заменяет более новые данные без предусмотренного требованиями признака.
12. Повторные быстрые нажатия «Подключиться» и «Обновить» не создают лишних
    соединений, дублей строк, гонок или падений.
13. При высокой частоте обновления интерфейс остаётся отзывчивым, потребление
    CPU/памяти приемлемо, события не теряются сверх допустимого порога.
14. Длительная работа и многократные reconnect не приводят к утечкам ресурсов,
    исчерпанию сокетов или деградации времени отклика.
15. Логи содержат адрес/порт, этап соединения и диагностируемые ошибки без
    секретов и избыточного потока на каждое штатное обновление.

## Выбранный критичный сценарий

**Успешное подключение к сервису и отображение 10 валидных сигналов.** Это
основная функция продукта и сквозная проверка всей цепочки: запуск процессов →
TCP-соединение → чтение и разбор данных → обновление модели → отображение в Qt.
Если сценарий не работает, пользователь не получает данные системы управления,
а остальные функции приложения теряют практический смысл.

Автотест проверяет наблюдаемый результат: после нажатия «Подключиться» в таблице
появляются ровно 10 строк, ID уникальны, имена/качество/время заполнены, а
значения преобразуются в число. Для изменяющихся сигналов намеренно не задано
точное значение. Сценарий отмечен маркерами `smoke`, `ui` и `linux`.

В Allure сценарий имеет продуктовое деление `Desktop signal monitor` (Epic) →
`TCP connection` (Feature) → `Display received signals` (Story). Это деление
описывает функцию продукта, тогда как pytest-маркеры используются для выбора
тестов по скорости, уровню и требованиям к окружению. Отдельный продуктовый
маркер для единственного сценария не добавлен.

## Подготовка Linux-окружения

Тест рассчитан на графическую сессию Linux с доступным AT-SPI. Для Ubuntu/Debian:

```bash
sudo apt-get install -y \
  accerciser at-spi2-core gir1.2-atspi-2.0 gir1.2-gtk-3.0 \
  python3-cairo python3-gi
gsettings set org.gnome.desktop.interface toolkit-accessibility true
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
python -m pip install -e .
npm install
```

Node.js и npm нужны только для установки Allure CLI и формирования отчёта.
Для запуска самого pytest-теста достаточно Python-зависимостей.

Qt-приложение запускается тестом с `QT_ACCESSIBILITY=1` и
`QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1`. После первого включения accessibility
может потребоваться перезапуск графической сессии. Перед запуском приложения
fixture дожидается состояния `LISTEN` для порта симулятора через `/proc/net/tcp`;
проверочное TCP-подключение намеренно не создаётся.

Для первого локального запуска предпочтительна Xorg-сессия. На GNOME Wayland
Dogtail дополнительно требует `gnome-ponytail-daemon`; без него координатный
клик по кнопке может быть недоступен.

## Запуск

```bash
python -m pytest -v \
  --alluredir allure-results --clean-alluredir \
  --app-cmd "/opt/signal-monitor/bin/signal-monitor" \
  --simulator-cmd "/opt/signal-simulator/bin/simulator --port 2001" \
  --simulator-port 2001 \
  --a11y-app-name "Signal Monitor"
```

Логи обоих процессов сохраняются независимо от результата в отдельном каталоге
`artifacts/<test-node-id>/`. Корневой каталог можно изменить параметром
`--artifacts-dir`.

Если доступное имя таблицы отличается от стандартного `Таблица сигналов`, его
можно передать отдельно:

```bash
python -m pytest -v ... --a11y-table-name "Signals"
```

Доступные имена элементов конкретной сборки удобно сначала посмотреть в
инспекторе accessibility `Accerciser`. Код завершает запущенные процессы даже
при падении проверки и сохраняет их stdout/stderr в каталоге артефактов.

## Allure-отчёт

После запуска теста сформируйте и откройте интерактивный отчёт:

```bash
npx allure generate allure-results
npx allure open allure-report
```

Конфигурация `allurerc.yaml` включает русскую локализацию и группировку по
Epic/Feature/Story. В отчёте видны четыре бизнес-шага сценария. Если тест падает,
его Allure-результат автоматически получает отдельные stdout/stderr-логи
приложения и симулятора; при успешном прохождении они остаются только в каталоге
`artifacts/`, чтобы не перегружать отчёт.

## Проверка вспомогательной логики

Unit-тесты не являются дополнительными продуктовыми сценариями. Они отдельно
проверяют разбор чисел и `/proc/net/tcp`, критерии готовности таблицы, граничные
значения и поведение условного ожидания:

```bash
python -m pytest -q unit_tests
```
